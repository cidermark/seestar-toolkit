# ENH-006 — Archive Dry-Run Reporting Improvements

**Specification date:** 2026-11-11

**Status:** Approved authoritative specification — implementation requires a separate explicit START instruction.

**Git ownership:** The user controls branch creation, commits, pushes, merges
and branch deletion.

## 1. Purpose and verified baseline

ENH-006 improves only the human-readable reporting produced by:

```text
seestar-toolkit archive SOURCE_ROOT ARCHIVE_ROOT --dry-run
```

The normal report becomes a concise overview followed by one compact block per
planned observation and a warning summary. Global `--verbose` retains the
detailed planned source-to-destination file mappings that normal dry-run output
currently prints. The report also makes the effective hierarchy template,
resolved observation destinations, planned light/stack file counts and raw
telescope metadata visible without requiring the user to interpret individual
file mappings.

This draft was prepared against repository `seestar-toolkit`, branch `main`, at
`35d1ef941b91ccff71bc07ddf5f4ac46aa52120c`, matching the requested reference
`35d1ef9`. `main` was aligned with `origin/main`, and the working tree was clean
at inspection. The inspected implementation uses one shared archive preparation
path and an immutable prepared plan for both dry-run reporting and execution.
The plan already contains the effective hierarchy template, observation
metadata and destinations, planned light files, optional planned stack, and
planning/discovery problems.

This document is a draft for user review. It does not approve or authorise
implementation, branch creation, commits, pushes, merges, releases or
publication.

## 2. Scope

### 2.1 Included

1. Reporting-only changes to `seestar-toolkit archive --dry-run`.
2. A concise normal dry-run overview.
3. A compact, clearly separated block for every planned observation.
4. Display of the effective archive hierarchy template exactly once.
5. Display of each planned observation's resolved destination.
6. Correct planned light-FITS and stacked-FITS file counts.
7. Display of raw telescope metadata when available and `unknown` otherwise.
8. Concise per-observation warning indication and a warning summary while
   preserving established observation-metadata, planning and discovery
   diagnostics.
9. Detailed planned file mappings when global `--verbose` is supplied.
10. Conservative `--convert-lights` dry-run reporting limited to facts that the
    existing preparation and collision-policy checks can reliably establish.
11. Focused automated tests for the reporting contract and preservation of
    established archive behavior.

### 2.2 Excluded

- Changes to archive discovery, classification, reconstruction, planning,
  execution, indexing or incremental reconciliation.
- A second discovery, reconstruction or planning pass, or a directory rescan
  performed solely to produce the report.
- Changes to prompts, interaction policy, exit codes, source actions, FITS
  collision policy, light-TIFF collision policy or error handling.
- Changes to telescope identity recognition, association or reconciliation,
  including inference of `S50` or `S50 Pro` from display metadata.
- Changes to hierarchy tokens, hierarchy semantics, destination planning,
  observation numbering or observing-night date policy.
- Changes to normal, non-dry-run archive execution output.
- New settings, persistent output-format preferences, machine-readable output
  or a stable parseable reporting interface.
- GUI work, archive verification or repair, archive reorganisation or
  migration, privacy-processing changes, or conversion-algorithm changes.
- Changes to FITS metadata, TIFF content, index content or any source/archive
  filesystem state.
- Unrelated refactoring, defects or features.

Any material requirement outside this boundary must be reported and separately
authorised rather than incorporated into ENH-006.

## 3. Unchanged behavior contract

ENH-006 must preserve the existing archive preparation and execution contract.
In particular:

- Dry-run uses the same discovery, classification, reconstruction, location
  resolution, metadata, planning, incremental reconciliation and destination
  calculation as the corresponding real archive invocation.
- Dry-run performs zero filesystem mutation. It creates or changes no archive
  directory, FITS, TIFF, index, candidate, temporary file or source file.
- Dry-run performs no FITS-to-TIFF conversion, candidate generation, converted
  TIFF validation, candidate-to-existing-TIFF comparison or prompt.
- The prepared archive result is the reporting authority. Reporting must not
  rediscover source files, reconstruct observations again, replan destinations
  or recursively inspect directories merely to calculate presentation data.
- Existing operational problems remain operational problems. Their established
  effect on exit status is unchanged.
- Existing exceptions, diagnostics, interactive location behavior, prompt
  policy and command-line usage behavior are unchanged.
- Copy/move semantics, FITS collision policies, light-TIFF collision policies,
  reconstruction rules, BUG-002/BUG-003 identity rules, archive hierarchy
  behavior, date policy, conversion behavior and index planning are unchanged.
- Normal archive execution without `--dry-run` retains its existing output and
  behavior, whether or not `--convert-lights` or global `--verbose` is present.

The normal dry-run report is intended for people. Its headings, spacing and
punctuation are not a stable parseable interface. Tests should assert required
information and ordering without turning illustrative formatting into a byte
contract.

## 4. Reporting data definitions

All counts and displayed values must be derived from the already prepared plan
and its existing observation-metadata diagnostics and discovery/problem
records.

### 4.1 Planned observations and files

- **Observation count:** `len(prepared.plan.observations)`.
- **Light FITS count for one observation:**
  `len(observation.lights)`. This is the count of planned individual-light
  files, normally discovered beneath the source `{DSO ID}_sub` directory.
- **Stacked FITS count for one observation:** `1` when
  `observation.stack is not None`; otherwise `0`. A planned stack is normally
  discovered beneath the source `{DSO ID}` directory.
- **Overall light/stack counts:** the sums of those per-observation values.

The FITS metadata value describing how many input frames contributed to a
stack is scientifically distinct from the number of stacked FITS files. It
must never be used as the stacked-FITS file count in ENH-006 reporting.

### 4.2 Observation fields

Every planned observation block must show:

1. observation name, such as `observation_01`;
2. logical target;
3. logical location;
4. session-end date;
5. telescope information;
6. resolved observation destination;
7. planned light-FITS count; and
8. planned stacked-FITS count.

When `observation.metadata.diagnostics` is non-empty, the affected observation
block must also indicate that warnings are present. The diagnostic text must
remain associated with that observation, either by listing it concisely in the
block or by using an unambiguous observation name in a final warning section.
The report must not silently discard these diagnostics.

The telescope display value is the raw telescope metadata already retained in
`observation.metadata.telescope`, after only the existing metadata handling
that produced the plan. If the retained value is absent, display `unknown`.
The reporting layer must not parse, normalise, recognise, relabel or infer a
model or device identity. A value such as `S50_99643794`,
`S50 Pro_edfe7fb2`, `Seestar S50` or another non-empty raw value is displayed
as retained. Missing data is `unknown`.

This presentation rule does not alter BUG-002/BUG-003 reconstruction or
reconciliation. The report must not claim that a displayed raw value is a
recognised identity unless an existing authoritative behavior already makes
that claim elsewhere; ENH-006 adds no such claim.

## 5. Normal dry-run reporting requirements

Without global `--verbose`, a successful or partially plannable dry-run must
present information in this conceptual order:

1. **Overall summary.** State that this is a dry-run and report the number of
   planned observations, total planned light FITS and total planned stacked
   FITS. Retain concise visibility of the effective source action and FITS
   collision policy.
2. **Effective hierarchy.** Show the effective hierarchy template exactly once,
   using the value from the prepared plan configuration. This is the template,
   not an inferred reconstruction from resolved paths.
3. **Observation blocks.** Emit one compact, visibly separated block per
   planned observation, in the deterministic order already supplied by the
   prepared plan. Each block contains every field in section 4.2.
4. **Index plan summary.** Preserve visibility of planned index output without
   printing a potentially noisy per-file FITS mapping. Existing planned index
   destinations may remain individually listed because they are distinct
   derived report products, not light/stack source mappings.
5. **Light-TIFF summary.** When `--convert-lights` is selected, add the
   conservative summary defined in section 7.
6. **Warning presentation and summary.** Indicate affected observations,
   preserve their diagnostic text and report the warning/problem totals and
   categories defined in section 8.

Normal output must not print individual light or stack source-to-destination
mapping lines. It must remain clear when multiple observations, including
observations from different telescopes, are present: each observation gets its
own named block and its own telescope, destination and counts. Values must not
be collapsed into a single telescope or destination summary.

An empty successful plan must still show a deterministic summary with zero
observations, zero planned light FITS and zero planned stacked FITS, followed by
the applicable warning summary. ENH-006 does not change whether any particular
empty or problematic input is operationally successful.

## 6. Verbose dry-run reporting requirements

When global `--verbose` is combined with `archive --dry-run`, the report must
contain everything required for normal dry-run output and additionally list
the detailed planned file mappings under their owning observation block.

For each `observation.lights` entry, report:

```text
FITS <source_path> -> <fits_destination>
```

For the optional `observation.stack`, report its FITS mapping and the already
planned stack-TIFF destination:

```text
FITS <source_path> -> <fits_destination>; TIFF -> <tiff_destination>
```

The exact indentation and labels are presentational, but every planned source
and destination currently available from the plan must remain visible in
verbose mode. Mappings must remain grouped by observation so that identical
basenames or multiple telescopes cannot be confused.

`--verbose` must not trigger extra discovery, FITS inspection, planning,
hashing, directory traversal, TIFF conversion or mutation. Existing debug log
behavior associated with global `--verbose` is outside this enhancement and
must remain compatible.

## 7. `--convert-lights` TIFF reporting limitations

When `--convert-lights` is selected, dry-run may report only these reliably
established categories under the current plan and FITS collision policy:

1. **Candidates without an existing destination TIFF.** These are planned
   light-TIFF candidates whose expected destination is currently absent.
2. **Existing TIFF destinations requiring comparison during real conversion.**
   These destinations exist, but dry-run has not generated a candidate and
   therefore has not established content identity or the eventual collision
   decision.
3. **Previously archived light FITS**, but only where the existing collision
   policy and current dry-run checks reliably establish that fact.

The report must use factual, conditional wording. Suitable concepts include:

```text
Candidates with no existing destination TIFF: 12
Existing TIFF destinations requiring comparison during real conversion: 3
Previously archived light FITS reliably identified: 2
```

Dry-run must never state or imply that it:

- converted a light FITS;
- created, validated or verified a TIFF;
- generated or compared a conversion candidate;
- established that an existing TIFF is identical or different;
- selected an interactive collision outcome; or
- guarantees that a TIFF will be created, replaced, preserved, skipped or
  otherwise successfully produced during real execution.

Accordingly, wording such as `would be created`, `will be created`, `already
present` when referring to content identity, `validated`, `verified`,
`converted` or `will be skipped` is prohibited unless it is explicitly framed
as an operation that still requires real conversion and the statement remains
true without candidate creation or comparison. The preferred report labels are
the factual category labels above.

ENH-006 must not broaden which archived lights are examined, alter hashing or
collision decisions, or add recursive archive maintenance. If an existing
category cannot be established safely under the active collision policy, it is
not counted as established merely to make the report more complete.

## 8. Warning and error presentation

### 8.1 Warning/problem summary

The normal report must end with a concise summary that separately counts:

- observation metadata diagnostics from each planned observation's
  `observation.metadata.diagnostics`;
- planning problems from `prepared.plan.problems`; and
- discovery problems from discovery items whose existing `problem` value is
  present.

The summary must include a total and all three category counts, including
zeros, so that a clean report is explicit. Each observation-metadata diagnostic
is counted once as one diagnostic entry; the implementation must not invent
additional warnings by splitting or reinterpreting its text. For example:

```text
Warnings: 3 total (1 observation metadata, 1 planning, 1 discovery)
```

or:

```text
Warnings: none (0 observation metadata, 0 planning, 0 discovery)
```

The established detailed diagnostic content must remain visible and must not
be discarded, rewritten into a misleading success statement or hidden behind
`--verbose`. Observation-metadata diagnostics must retain their text and an
unambiguous association with the affected observation. This includes existing
diagnostics for conflicting FITS target evidence, conflicting source GPS
evidence, and absence of target evidence where planning uses the explicit
`unknown` fallback. The report must show the planned `unknown` target and retain
the reason it was selected; it must not present the fallback as if no warning
existed. Planning problems must remain identifiable as planning problems;
discovery problems must retain their source path and problem text. Detailed
diagnostics should continue to use standard error, preserving the current
stdout/stderr distinction, while concise per-observation warning indications
and the aggregate summary belong with the human-readable dry-run report on
standard output.

ENH-006 must report only diagnostics already retained in the prepared result.
It must not invent warning text, reinterpret evidence, reopen FITS files, rerun
metadata derivation or invoke discovery, reconstruction or planning again to
produce warnings.

Repeated references to the same already-recorded problem must not be generated
merely by reporting. ENH-006 does not introduce diagnostic de-duplication that
would alter the authoritative problem collections.

### 8.2 Errors and exit status

Errors raised before a prepared plan can be reported retain the current
`Error: ...` handling and operational exit status. Command-line usage errors
retain the existing parser behavior. A prepared plan with operational problems
retains its existing non-zero result; a prepared plan without operational
problems retains its existing success result. Report formatting must not
promote a failure to success or convert a warning/problem into a new failure.

## 9. Illustrative output — non-byte-contractual

The following examples illustrate required content and grouping. They are
**not byte-for-byte output contracts**. Exact punctuation, indentation, path
formatting and headings may be refined during a separately authorised
implementation, provided sections 4–8 remain satisfied.

### 9.1 Normal dry-run

```text
Archive dry run
Summary: 2 observations; 27 light FITS; 2 stacked FITS; action=copy; collision=skip-identical
Hierarchy: {target}/{location}/{session_end_date}

Observation observation_01
  Target: M 27
  Location: Warfield
  Session end: 2026-09-03
  Telescope: S50_99643794
  Destination: /archive/M 27/Warfield/20260903/observation_01
  Files: 12 light FITS; 1 stacked FITS

Observation observation_02
  Target: M 27
  Location: Warfield
  Session end: 2026-09-03
  Telescope: S50 Pro_edfe7fb2
  Destination: /archive/M 27/Warfield/20260903/observation_02
  Files: 15 light FITS; 1 stacked FITS

Index: /archive/M 27/INDEX.md
Warnings: none (0 observation metadata, 0 planning, 0 discovery)
```

### 9.2 Verbose dry-run excerpt

```text
Observation observation_01
  Target: M 27
  Location: Warfield
  Session end: 2026-09-03
  Telescope: S50_99643794
  Destination: /archive/M 27/Warfield/20260903/observation_01
  Files: 1 light FITS; 1 stacked FITS
  Planned mappings:
    FITS /source/M 27_sub/Light_001.fit -> /archive/M 27/Warfield/20260903/observation_01/fits_images/lights/Light_001.fit
    FITS /source/M 27/Stacked_001.fit -> /archive/M 27/Warfield/20260903/observation_01/seestar_stacked/Stacked_001.fit; TIFF -> /archive/M 27/Warfield/20260903/observation_01/seestar_stacked/Stacked_001.tiff
```

### 9.3 Missing telescope and light-TIFF limitations

```text
Observation observation_03
  Target: unknown
  Location: unknown
  Session end: 2026-10-15
  Telescope: unknown
  Destination: /archive/unknown/unknown/20261015/observation_03
  Files: 20 light FITS; 0 stacked FITS
  Warnings: 1 (details reported below for observation_03)

Light TIFF candidates
  Candidates with no existing destination TIFF: 17
  Existing TIFF destinations requiring comparison during real conversion: 3
  Previously archived light FITS reliably identified: 2

Observation warning — observation_03: No target evidence; using explicit unknown fallback
Warnings: 1 total (1 observation metadata, 0 planning, 0 discovery)
```

The example deliberately does not claim that 17 TIFFs will be created or that
the three existing destinations will be skipped, replaced or found identical.

## 10. Performance and implementation constraints

1. Render the report from the single `PreparedSeestarArchive` already produced
   by `_run_archive` and the existing planned-index calculation.
2. Do not call `prepare_seestar_archive`, discovery, reconstruction or planning
   a second time for reporting.
3. Do not rescan source or archive directories solely for counts, telescope
   display, observation grouping or file mappings.
4. Do not reopen FITS files solely for report fields already retained in the
   plan.
5. Do not hash files except where the existing conservative
   `light_tiff_dry_run_counts` behavior already requires hashing to establish
   previously archived light FITS under the active collision policy. ENH-006
   must not broaden that work.
6. Report generation, excluding already-established light-TIFF collision
   checks, must be linear in the number of prepared observations, planned files
   and recorded problems, with bounded additional state.
7. Normal mode must avoid constructing or emitting detailed per-file mapping
   text that it will not display. Verbose mode may format each planned mapping
   once.
8. Preserve deterministic prepared-plan ordering. Do not sort by a new field in
   the reporting layer.

## 11. Focused test scenarios

Implementation tests must cover at least the following scenarios without
weakening existing tests.

| ID | Scenario | Required evidence |
|---|---|---|
| R01 | Single observation, normal dry-run | Overall summary, hierarchy once, complete observation block, no per-file mappings. |
| R02 | Single observation, verbose dry-run | Normal content plus every planned light and stack mapping, grouped under its observation. |
| R03 | Multiple observations/telescopes | Separate named blocks retain each raw telescope value, destination and counts. |
| R04 | Missing telescope metadata | Display is exactly the chosen `unknown` presentation; no model is inferred. |
| R05 | Raw generic/unrecognised telescope value | Raw retained value is displayed without identity/model claims or normalisation. |
| R06 | Lights-only observation | Light count is `len(observation.lights)` and stacked-FITS count is `0`. |
| R07 | Stack-only or stack-present observation | Stacked-FITS count is `1`, irrespective of reported stack-input metadata count. |
| R08 | Alternative configured hierarchy | Effective template appears once and resolved destinations follow the prepared plan. |
| R09 | Observation-metadata, planning and discovery diagnostics | Summary totals and all three categories are correct; established text remains visible on stderr with observation diagnostics unambiguously associated with the affected observation; exit code is unchanged. |
| R09a | Conflicting target/GPS evidence and absent target evidence | Existing diagnostic text is preserved without invention; affected observations are identified; an absent target displays the planned `unknown` fallback and its retained reason. |
| R10 | Clean plan | Explicit zero-warning summary is present. |
| R11 | Empty prepared plan | Deterministic zero counts; existing empty-input exit semantics and zero mutation are preserved. |
| R12 | `--convert-lights`, no destination TIFF | Counted as a candidate with no existing destination, without conversion or creation claims. |
| R13 | `--convert-lights`, existing TIFF destination | Counted as requiring comparison during real conversion; no candidate comparison, prompt or outcome claim. |
| R14 | Previously archived light FITS across relevant collision policies | Count is reported only where current checks reliably establish it; established policy behavior is unchanged. |
| R15 | Dry-run zero mutation | No source/archive/TIFF/index/temp changes in normal and verbose modes. |

| R17 | Normal real archive execution | Existing output remains unchanged with and without global `--verbose`. |

Focused tests should prefer semantic assertions over a complete multiline
snapshot. They must still be strict about required values, absence of normal
mode mappings, conservative TIFF language, observation grouping and warning
channel behavior.

## 13. Implementation boundary and user-controlled Git workflow

Implementation is not authorised by this draft. Approval of wording, discussion
of design, or a request to revise this document does not constitute permission
to edit source code or tests.

Implementation requires a separate, explicit user `START` instruction. After
that instruction, the user controls creation of the implementation branch:

```text
enh/ENH-006-archive-dry-run-reporting
```

Codex must not create or switch to that branch unless explicitly instructed by
the user. Commits, pushes, merges and branch deletion likewise remain under
user control and require explicit instruction. Any authorised implementation
must remain limited to ENH-006, follow the project's tests-first workflow, run
the complete `pytest` suite and `ruff check .`, and report results without
claiming approval or closure that the user has not granted.
