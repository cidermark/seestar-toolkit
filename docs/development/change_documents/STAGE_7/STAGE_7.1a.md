## 1. Purpose

Stage 7.1a defines the authoritative architecture, terminology, configuration model, safety policies, and handoff contracts for Stage 7 — Archive organisation and file management.

This is primarily a contract/documentation stage. It must make later Stage 7 implementation mechanical wherever practical: later sub-stages should implement agreed rules rather than invent archive policy.

Stage 7.1a must not prematurely implement the archive engine, observation reconstruction, filesystem placement, archive CLI, reverse geocoding, or target index generation.

## 2. Stage 7 boundaries

Stage 7 owns:

- discovery and interpretation of Seestar archive input beneath a defined input root;
- reconstruction of observations from Seestar files;
- creation and management of the image archive hierarchy;
- user-configurable archive hierarchy ordering;
- archive metadata resolution;
- safe placement of original FIT/FITS files;
- placement of Toolkit-generated TIFF derivatives;
- preservation of Seestar-generated stacked FITS;
- duplicate/collision policy;
- copy/move policy;
- dry-run behaviour;
- archive-oriented CLI workflow;
- human-readable archive indexes.

Stage 7 must **not**:

- change Stage 6 `convert` behaviour;
- change Stage 6 `convert-batch` behaviour;
- make Stage 6 batch conversion recursive;
- perform broad real-dataset qualification (Stage 8);
- perform packaging/release work (Stage 9);
- implement DSLR ingestion.

The Stage 7 architecture should, however, avoid unnecessary assumptions that would prevent later DSLR/other-camera support.

## 3. Terminology

The following terms are normative for Stage 7.

### 3.1 Session

A **session** is an observing night/period at a location. A session may contain multiple targets and multiple observations of the same target.

### 3.2 Session end date

`session_end_date` is the archive grouping date derived from capture time using:

```text
session_end_date = date(capture_datetime + 12 hours)
```

This deliberately groups captures spanning midnight into the same observing-night date.

Examples:

```text
2026-09-01 22:00 -> 20260902
2026-09-02 01:30 -> 20260902
2026-09-02 05:00 -> 20260902
```

This rule affects **archive directory placement only**.

Stage 7 must never alter original FITS timestamps, image metadata, or TIFF metadata merely to implement this grouping rule.

### 3.3 Target

The astronomical object being imaged, derived from authoritative metadata where available.

### 3.4 Observation

An **observation** is one discrete imaging capture/run of one target.

A target may have multiple observations during the same session.

### 3.5 Light

A **light** is an individual source sub-exposure belonging to an observation.

### 3.6 Seestar stack

A **Seestar stack** is the stacked product generated automatically by the Seestar for an observation.

It must be distinguished from products later generated by Siril or other astronomy applications.

## 4. Archive hierarchy

### 4.1 User-configurable hierarchy

The archive hierarchy must not be hard-coded.

The default hierarchy is:

```text
{target}/{location}/{session_end_date}
```

Alternative orderings must be possible, including:

```text
{location}/{session_end_date}/{target}
```

The hierarchy must be represented through configuration rather than separate hard-coded code paths.

The configuration model must be reusable by both the CLI and a possible future UI.

### 4.2 Toolkit-managed observation structure

Beneath the configured target/location/session hierarchy, the Toolkit manages observation directories.

An observation directory is always present, including for the first observation:

```text
observation_01
observation_02
...
```

The Toolkit must not initially omit `observation_01` and later restructure the archive if a second observation appears.

### 4.3 Canonical structure

The default conceptual structure is:

```text
ARCHIVE_ROOT/
└── {target}/
    ├── INDEX.md
    └── {location}/
        └── {session_end_date}/
            ├── observation_01/
            │   ├── lights/
            │   ├── seestar_stacked/
            │   └── tiff/
            └── observation_02/
                ├── lights/
                ├── seestar_stacked/
                └── tiff/
```

### 4.4 `lights/`

Original individual Seestar light FIT/FITS files are placed directly in `lights/`.

There must not be an additional `source/` or `fits/` layer beneath `lights/`.

This is intentional so the archived observation remains convenient for astronomy stacking software, including Siril workflows that expect source lights in a `lights` directory.

The architecture should permit future sibling frame-type directories such as:

```text
darks/
flats/
biases/
```

but Stage 7 need not create unused directories or implement calibration-frame ingestion.

### 4.5 `seestar_stacked/`

The original Seestar-generated stacked FITS and its Toolkit-generated TIFF derivative are kept together:

```text
seestar_stacked/
├── <original-seestar-stack-name>.fit
└── <original-seestar-stack-name>.tiff
```

The name `seestar_stacked` is deliberate: it identifies the provenance of the stack and distinguishes it from later application-generated stacks.

### 4.6 `tiff/`

TIFF derivatives generated from individual light FITS are placed in:

```text
tiff/
```

A TIFF generated from the Seestar stacked FITS is **not** placed here; it belongs beside its FITS source in `seestar_stacked/`.

## 5. Filename policy

### 5.1 Preserve original FITS filenames

Stage 7 should preserve original Seestar FIT/FITS filenames wherever practical.

For example:

```text
Light_IC 434_10.0s_LP_20260103-220259.fit
```

remains:

```text
lights/Light_IC 434_10.0s_LP_20260103-220259.fit
```

### 5.2 TIFF derivative names

Generated TIFF files inherit the source basename and replace the FIT/FITS extension with `.tiff`.

Example:

```text
Light_IC 434_10.0s_LP_20260103-220259.fit
->
Light_IC 434_10.0s_LP_20260103-220259.tiff
```

For a stack:

```text
Stacked_195_IC 434_10.0s_LP_20260103-225603.fit
->
Stacked_195_IC 434_10.0s_LP_20260103-225603.tiff
```

## 6. Path-component normalisation

Metadata-derived path components such as `{target}` and `{location}` must be normalised deterministically and safely.

Required policy:

- remove leading/trailing whitespace;
- collapse repeated internal whitespace to one ordinary space;
- preserve ordinary single spaces;
- preserve useful human readability;
- do not automatically remove all spaces;
- do not automatically replace spaces with underscores;
- prevent `/` or equivalent separators from creating unintended hierarchy levels;
- reject or replace filesystem-unsafe characters according to a documented deterministic rule;
- prevent `.` and `..` path components;
- prevent absolute-path or path-traversal escape from the archive root.

Examples:

```text
"  IC 434  "        -> "IC 434"
"NGC   7000"        -> "NGC 7000"
"Horse Head Nebula" -> "Horse Head Nebula"
```

The same normalisation principles should apply consistently to target and logical location names.

## 7. Seestar input-root contract

### 7.1 Root input

The archive process uses the parent Seestar work directory as its root input.

Typical example:

```text
My Works/
```

The root contains all target/product and target-sub directories to be processed.

Example:

```text
My Works/
├── IC 434/
│   ├── Stacked_195_IC 434_10.0s_LP_20260103-225603_thn.jpg
│   ├── Stacked_195_IC 434_10.0s_LP_20260103-225603.fit
│   └── Stacked_195_IC 434_10.0s_LP_20260103-225603.jpg
└── IC 434_sub/
    ├── Light_IC 434_10.0s_LP_20260103-220259_thn.jpg
    ├── Light_IC 434_10.0s_LP_20260103-220259.fit
    ├── Light_IC 434_10.0s_LP_20260103-220259.jpg
    └── ...
```

Mosaic light directories are expected to have a related Seestar naming convention, provisionally such as `<target>_mosaic_sub`; the exact real-world convention should be confirmed before relying on it.

### 7.2 Stage 6 remains unchanged

Understanding this known shallow Seestar structure in Stage 7 does not change the Stage 6 flat, non-recursive `convert-batch` contract.

## 8. Input discovery and classification contract

Stage 7 must be able to distinguish at least:

- individual light FIT/FITS;
- Seestar stacked FIT/FITS;
- Seestar full-size JPEG;
- Seestar thumbnail JPEG (`*_thn.jpg`);
- unrelated/unknown files.

Filename and directory conventions are useful evidence, but must not be the sole authority where FITS inspection/classification can provide stronger evidence.

The intended evidence hierarchy is broadly:

```text
FITS inspection/classification
        +
directory context
        +
filename structure
        ->
final classification
```

Exact implementation belongs to Stage 7.1b.

## 9. Observation reconstruction contract

### 9.1 Source directories do not define observations

The Seestar may place captures of the same target into the same target and `_sub` directories regardless of capture date/time.

Therefore one source directory pair may contain several distinct observations.

Stage 7 must reconstruct observations from file evidence rather than equating a directory with an observation.

### 9.2 Stacked FITS as observation-end marker

A recognised Seestar stacked FITS is the **primary observation-end marker** when available.

Verified example:

```text
First light:   20260103-220259
...
Final light:   20260103-225601
Stacked FITS:  20260103-225603
```

The stack timestamp occurs seconds after the final light and provides a natural observation boundary.

Normative rule:

> Each recognised Seestar stacked FITS acts as the endpoint of an observation. Compatible preceding, as-yet-unassigned light subs are associated with that observation.

### 9.3 Stack count

A stack filename may contain the number of images used by Seestar, e.g.:

```text
Stacked_195_...
```

This count is supporting/validation information only.

It must **not** be used as a rule to take exactly the preceding N light files because Seestar may reject captured subs from its stack.

### 9.4 Supporting evidence

Observation reconstruction may use:

- target identity;
- light timestamps;
- stacked-image timestamp;
- exposure time;
- filter;
- capture cadence;
- FITS metadata;
- capture mode;
- stack count as a consistency check.

Exact reconstruction logic belongs to Stage 7.1c.

### 9.5 Missing stack fallback

Stage 7 must not require a stacked FITS to exist in every case.

If lights exist without a usable stacked FITS, later implementation must provide a safe fallback using temporal/cadence and compatible metadata evidence.

Ambiguous grouping must not be silently guessed.

Interactive workflows may request confirmation. Non-interactive workflows must use an explicitly defined safe policy, such as reporting/failing the ambiguous group rather than inventing certainty.

## 10. Intentional observation merging — MUST BE USER-DOCUMENTED

This behaviour is an important Stage 7 feature and must be prominently documented in eventual user-facing documentation.

Because recognised Seestar stacked FITS files define observation boundaries, a user can intentionally merge compatible consecutive Seestar captures into one archive observation by ensuring that only the **final** stacked FITS remains eligible for Stage 7 discovery.

Conceptually:

```text
capture 1 lights
capture 2 lights
capture 3 lights
final recognised stacked FITS
        ->
one reconstructed observation
```

Normative rule:

> Multiple recognised Seestar stacks create multiple observation boundaries. If only the final stack remains eligible for discovery, compatible preceding unassigned lights may be grouped into the single observation ending at that final stack.

This changes archive grouping only. It does not modify or combine the source FITS files.

Stage 7 must not promise that an arbitrary filename rename will hide a stack if classification can still identify it. User documentation must define a reliable method for making intermediate stacks ineligible, such as moving them outside the input root, changing them to a deliberately unsupported extension, or a future explicit exclusion mechanism.

Compatibility checks must still prevent obviously incompatible data from being merged merely because intermediate stacks are absent.

## 11. Location-resolution policy

`{location}` is a human-friendly logical archive location. It is separate from the precise GPS coordinates recorded by the capture.

Resolution precedence is:

```text
1. Explicit CLI/user-supplied location
        ↓
2. Nearest matching saved/configured location
        ↓
3. Optional reverse-geocoded suggestion
   ├── accept
   └── reject -> enter preferred name
        ↓
4. Interactive manual location entry
        ↓
5. "unknown"
```

### 11.1 Explicit location

An explicitly supplied logical location always wins.

### 11.2 Saved locations

Configuration must support multiple named locations, each with:

- logical name;
- latitude;
- longitude;
- matching radius.

Conceptual TOML:

```toml
[[locations]]
name = "Home"
latitude = 51.41234
longitude = -0.75123
radius_m = 250

[[locations]]
name = "Warfield Church"
latitude = 51.42010
longitude = -0.74280
radius_m = 150
```

Hundreds of entries are acceptable; such a configuration remains small.

If matching radii overlap, the **nearest matching configured location wins**. File ordering must not determine the result.

### 11.3 Reverse geocoding

Reverse geocoding is an optional convenience, not an archive requirement.

Architecture must not hard-wire Stage 7 to one public geocoding provider.

In an interactive workflow, a reverse-geocoded name must be presented as a suggestion that the user can accept or reject.

### 11.4 Manual entry

If automatic resolution does not produce an accepted result, interactive operation may ask for a logical location name.

### 11.5 Unknown

If location remains unresolved:

```text
location = "unknown"
```

is valid.

Missing location alone must not prevent archiving.

### 11.6 Non-interactive behaviour

Non-interactive operation must never wait for keyboard input. Interactive-only steps are skipped or governed by explicit non-interactive policy.

### 11.7 Preserve precise coordinates

The archive metadata model should retain the exact capture coordinates separately from the logical location name wherever they are available.

## 13. JPEG policy

Seestar generates both full-size JPEGs and thumbnail JPEGs.

Stage 7 must recognise them separately even if the initial handling policy is the same.

Conceptual classifications:

```text
SEESTAR_JPEG
THUMBNAIL_JPEG
```

Supported policy concepts should include:

- `keep` — archive the JPEG;
- `discard` — explicitly remove it under a deliberate destructive policy;
- `ignore` — leave it untouched in the source input.

The safe initial/default policy is:

```text
ignore
```

Stage 7 must not automatically delete JPEGs by default.

A later user-selectable discard policy may be supported, but destructive behaviour must be explicit.

---

## 14. Source copy/move policy

The safe default source action is:

```text
copy
```

An explicit `move` action may be supported later in Stage 7.

Move semantics must ensure that a source is removed only after successful destination creation and required validation.

No archive operation may silently destroy an original astronomical image.

---

## 15. Source compression policy

Compression of archived originals is not a Stage 7.1a implementation requirement.

The architecture should permit a future source-storage policy such as:

```text
copy
move
gzip
```

but compression must not be adopted automatically without measuring representative Seestar FITS compression behaviour and considering usability for stacking software.

Possible formats discussed include `.gz`, `.tgz`, and `.zip`.

Individual gzip compression may be more convenient for selective restoration; session archives may reduce filesystem entries but make individual access less convenient.

For Stage 7, uncompressed source preservation remains the baseline unless a later agreed sub-stage explicitly changes this.

---

## 16. Duplicate and collision policy

### 16.1 Identical destination file

If an incoming source maps to an existing destination file and the content is byte-for-byte identical, later implementation should offer the conceptual choices:

```text
Skip
Overwrite
Cancel
```

`Skip` is the safe/default recommendation.

Content identity should use a reliable content comparison such as SHA-256 rather than filename, timestamp, or size alone.

### 16.2 Same name, different content

If the destination filename exists but contains different content:

- Stage 7 must never silently overwrite it;
- the condition must be reported clearly;
- safe resolution may include cancelling or selecting/creating another observation;
- destructive overwrite of a different astronomical source must not be the normal/default path.

### 16.3 Re-import

Accidental re-import of the same target/observation should therefore be safely detectable and recoverable without needless duplication or silent destruction.

---

## 17. Dry-run contract

Dry-run must execute the same planning path as a real archive operation wherever practical:

- input discovery;
- FITS inspection/classification;
- observation reconstruction;
- location resolution that does not require forbidden interaction;
- metadata normalisation;
- hierarchy/path planning;
- duplicate/collision detection;
- planned TIFF placement;
- planned copy/move actions.

Dry-run must perform **zero filesystem mutation**.

It must not:

- create directories;
- copy files;
- move files;
- delete files;
- overwrite files;
- generate archive TIFF files;
- update archive indexes.

Its output should clearly describe what a real run intends to do.

---

## 18. Archive metadata model and future DSLR compatibility

Stage 7 implementation supports Seestar FIT/FITS input.

However, the archive metadata model should be source-format-neutral where practical.

Conceptually, later archive planning should be able to operate on normalised metadata such as:

```text
source_path
target
location
capture_coordinates
capture_datetime
session_end_date
observation
frame_type
source_format
telescope_identifier
derived_files
```

A Seestar-specific layer obtains these values from FITS metadata, directory context, and filename evidence.

A future DSLR layer could obtain corresponding values from EXIF plus user/session metadata.

Stage 7 must not implement DSLR ingestion, but should avoid making the archive engine inherently dependent on Seestar filenames or FITS-only path concepts.

## 19. Human-readable target index contract

Stage 7 will later generate a human-readable index at target level:

```text
{target}/INDEX.md
```

The index is a derived convenience document, not an authoritative metadata source. It should be safely regenerable from archived observations.

It should support multiple locations, sessions, and observations for the target.

A representative observation entry should include available metadata such as:

```text
# IC 434

## Warfield — 2026-01-04

### Observation 01

- Telescope: S50_99643794
- First light: 2026-01-03 22:02:59
- Last light: 2026-01-03 22:56:01
- Exposure: 10.0 s
- Filter: LP
- Light subs: 201
- Seestar stack: Stacked_195_IC 434_10.0s_LP_20260103-225603.fit
- Seestar stack count: 195
- Capture mode: Alt-Az
- GPS: 51.xxxxx, -0.xxxxx
```

The `Telescope` value should use the actual captured telescope identifier where available, for example:

```text
S50_99643794
```

rather than a generic model label such as `ZWO Seestar S50`.

If the identifier is unavailable, use `unknown` rather than guessing.

Exact index implementation belongs to Stage 7.1h.
