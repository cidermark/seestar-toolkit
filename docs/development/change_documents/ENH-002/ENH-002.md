# ENH-002 — Configurable Observing-Night Date Policy

**Specification date:** 2026-10-07
**Status:** Authoritative specification; implementation not started
**Git ownership:** User controls branch creation, commits, pushes, merges and branch deletion.

## 1. Purpose and baseline

ENH-002 adds a persistent archive preference that selects whether an observing
night is identified by its calendar start date or calendar end date. It makes the
existing convention configurable while retaining that convention as the built-in
default.

This specification was prepared against `main` at
`3089a5cc5292658351d61ee0fb3e35156611c0d5`, with a clean working tree. It is a
documentation-only deliverable and is not evidence that implementation has
started or that ENH-002 functionality exists in a release.

The authoritative public setting is:

```text
archive.observation_date_policy
```

Its only valid values are `start` and `end`; the built-in default is `end`.
The earlier provisional name `archive.observing_night_date` was rejected and is
not a setting to implement, display, persist or support.

## 2. Scope

### Included

1. An `archive.observation_date_policy` preference integrated with the
   configuration-management facilities delivered by ENH-001.
2. A fixed noon observing-night boundary and `start`/`end` date resolution.
3. Propagating the resolved observing-night date through the existing archive
   planning path and its current consumers.
4. Configuration, boundary, archive-planning and regression validation, plus
   the required development and user documentation updates at implementation
   time.

### Excluded

- Existing-archive regeneration, reorganisation or migration.
- Configurable rollover times, sunset/sunrise calculations, timezone redesign
  or GPS-to-timezone mapping.
- Changes to authoritative timestamp selection, FITS timestamp parsing,
  filename timestamp fallback, timezone normalisation or timestamp-conflict
  diagnostics.
- Changes to Observation reconstruction, compatibility/association or
  telescope identity; S50 Pro support; S50/S50 Pro Device Name investigation;
  acquisition-stream detection; location-consistency work; FITS anonymisation;
  or `archive --convert-lights`.
- A per-run archive CLI override, unrelated ENH-001 configuration expansion or
  unrelated archive restructuring.

Any material defect or necessary out-of-scope change found during implementation
must be reported and dispositioned, not silently incorporated.

## 3. Observing-night model

Noon is the fixed practical boundary between observing nights. For an observing
night spanning the 5th and 6th:

```text
5th 12:00:00 <= capture < 6th 12:00:00
```

the policies produce `start -> 5th` and `end -> 6th`. Applied to the existing
authoritative datetime representation, the equivalent calculations are:

```text
start -> date(authoritative_datetime - 12 hours)
end   -> date(authoritative_datetime + 12 hours)
```

The noon boundary is a deliberately safe practical separator for normal
deep-space observing. ENH-002 must not expand this into astronomical,
sunset/sunrise or location-dependent boundary calculation. Month-end and
year-end behaviour uses normal datetime arithmetic.

### Required boundary results

| Capture | `start` | `end` |
|---|---:|---:|
| 5th 11:59:59 | 4th | 5th |
| 5th 12:00:00 | 5th | 6th |
| 5th 12:00:01 | 5th | 6th |
| 5th 23:59:59 | 5th | 6th |
| 6th 00:00:00 | 5th | 6th |
| 6th 00:00:01 | 5th | 6th |
| 6th 11:59:59 | 5th | 6th |
| 6th 12:00:00 | 6th | 7th |

## 4. Configuration contract

The TOML representation is:

```toml
[archive]
observation_date_policy = "start"
```

or:

```toml
[archive]
observation_date_policy = "end"
```

Reuse the existing `config show`, `config show --saved`, `config show
--defaults`, `config set` and `config unset` behaviours and response
conventions. Do not introduce a separate configuration mechanism.

The effective precedence is:

```text
saved configuration -> built-in default
```

There is deliberately no archive-command override. The preference is persistent
archive policy, changed through configuration management.

`start` and `end` are interpreted case-insensitively. `config set` accepts, for
example, `START`, `Start` and `start`, validates them as the same value, and
persists canonical lowercase. Manually edited TOML is likewise interpreted
case-insensitively, but reading it must not rewrite it merely to change case.
Invalid known values remain configuration errors and must never silently fall
back to `end`. Existing ENH-001 whitespace and validation conventions remain
applicable.

### Backwards compatibility

`end` preserves the existing calculation `date(capture_datetime + 12 hours)`.
Consequently, each of the following resolves to `end`:

- No configuration file.
- A configuration file without `observation_date_policy`.
- Pre-ENH-002 configuration.
- An explicitly saved `end` value.
- An unset configuration value.

## 5. Architecture and downstream behaviour

ENH-002 must use the same authoritative datetime currently supplied to archive
planning. It must not alter timestamp authority, FITS parsing, filename fallback,
timezone interpretation or normalisation, or timestamp-conflict diagnostics.

Repository inspection established that the calculated observing-night date
currently affects archive planning grouping, hierarchy destination paths,
incremental Observation reconciliation, the collision namespace, dry-run
output and target-index date grouping. It does not take part in reconstruction
compatibility or association: date calculation occurs after reconstruction.

The implementation must preserve this architecture. Resolve the selected policy
once in the existing observing-night date calculation and supply that date to
existing downstream consumers. Do not duplicate date-policy logic in individual
consumers. A broad rename/refactor of existing internal `session_end_date`
terminology is neither required nor prescribed merely because `start` becomes
available; new public-facing terminology must use `observation_date_policy`.

The smallest coherent extension is expected to extend `ArchiveConfig`, defaults
and validation; extend managed preferences using existing case normalisation;
make the existing date calculation policy-aware; and pass the resolved policy
through the current planning path while preserving `end` by default.

## 6. Existing archives and reporting

ENH-002 is prospective only. Changing the preference saves the new setting and
affects later archive processing, but does not scan archive content, rename
directories, move files, reorganise archives or reconcile hierarchies created
under different policies. Re-archiving the same material after a policy change
may therefore create or use a differently dated hierarchy; this is accepted
behaviour.

Existing-archive regeneration/reorganisation is a separate planned enhancement.
That future work should take the saved `observation_date_policy` into account.

Do not add routine archive or dry-run policy messages. Existing output remains
structurally unchanged: the selected date naturally appears where current
destination paths, dry-run reporting and indexes already show it.

at least the following:

| ID | Required evidence |
|---|---|
| D01 | Built-in `end` default, missing configuration and pre-ENH-002 configuration lacking the setting resolve to `end`. |
| D02 | Explicit `start` and explicit `end` resolve correctly; `config unset` restores `end`. |

| D04 | Invalid known values fail as configuration errors; existing ENH-001 whitespace and validation behaviour remains intact. |

| D06 | Month-boundary and year-boundary transitions use ordinary datetime arithmetic. |
| D07 | Regression evidence proves `end` preserves current +12-hour behaviour, including first-light timestamp precedence and stack-only fallback. |
| D08 | Planning/grouping, destination hierarchy, affected incremental/reconciliation behaviour, dry-run behaviour and index grouping consume the selected date through the existing path. |
| D09 | No archive CLI override or duplicated downstream policy calculation has been added; changing policy does not reorganise existing archives. |
| D10 | Normal project lint, formatting and test validation passes. |

Use focused unit/integration fixtures for date boundaries, configuration state and
planning effects. At closure, run the repository-mandated checks and do not
invent passing totals or claim checks not performed.
