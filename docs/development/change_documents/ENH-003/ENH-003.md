# ENH-003 — Optional Archive Light-TIFF Conversion

**Specification date:** 2026-10-09

**Status:** Authoritative specification; implementation not started

**Git ownership:** User controls branch creation, commits, pushes, merges and branch deletion.

## 1. Purpose and baseline

ENH-003 adds an explicit invocation-only archive capability:

```text
seestar-toolkit archive --convert-lights SOURCE_ROOT ARCHIVE_ROOT
```

The option creates TIFF derivatives for eligible individual-light FITS in
addition to preserving the original FITS. Normal archive operation continues
to preserve individual-light FITS without automatically creating light TIFFs.
No persistent configuration preference is added.

This specification was prepared against clean `main` at
`18129d25e71c44ce5f05d636f02bcf8f0bdd60cd` —
`18129d2 docs: record ENH-002 completion` — with `main` aligned with
`origin/main`. It is a documentation-only deliverable. It does not authorise or
constitute implementation, branch creation, a commit, a release or publication.

Repository inspection established the following implementation baseline:

- Archive planning currently places individual lights in
  `observation_NN/lights/`, retains a planned but unused `tiff/` directory
  field, and places the stack FITS and TIFF together in `seestar_stacked/`.
- Incremental reconciliation, observation recognition, device-identity
  inspection and index generation currently recognize the historical
  `lights/` path explicitly.
- The integrated archive workflow already converts an eligible archived stack
  FITS through the authoritative `convert_fits_to_tiff()` service after FITS
  execution. The conversion service, not archive orchestration, owns FITS
  reading, demosaicing/RGB normalization and TIFF writing.
- Existing stack derivative eligibility is `COPIED`, `MOVED` or
  `SKIPPED_IDENTICAL`; existing orchestration treats every `PARTIAL` original
  outcome as ineligible and treats an existing TIFF as a collision.
- FITS execution already uses verified staging and atomic replacement;
  `SKIPPED_IDENTICAL` is SHA-256 verified. Index writes use their own atomic
  temporary-file path.

Those facts describe the starting point, not reasons to preserve behavior that
this specification explicitly changes.

## 2. Scope

### Included

1. The archive-only `--convert-lights` flag and help text.
2. The new archive observation layout for every newly planned observation.
3. Optional conversion of eligible individual lights from their authoritative
   archived FITS through the existing FITS-to-TIFF pipeline.
4. Safe candidate generation, digest comparison, promotion, replacement,
   collision decisions and cleanup.
5. Narrow processing of previously archived identical light FITS encountered
   during the current archive operation.
6. Consistent planning, incremental reconciliation, archive observation
   recognition and indexing under the new layout.
7. Aggregate reporting, diagnostics and exit status for light derivatives.
8. Focused automated and documentation validation needed for this behavior.

### Excluded

- Migration, regeneration or reorganization of historical archives, including
  archives using `observation_NN/lights/`.
- Backward-compatible recognition of the historical `lights/` layout as an
  ENH-003 archive observation.
- Recursive archive TIFF maintenance or a general archive verification command.
- Archive anonymization, acquisition-stream detection, observing-night policy
  changes, S50/S50 Pro identity changes, DSLR support, calibration frames,
  Solar/Lunar/planetary workflows or Siril integration.
- A persistent `convert-lights` preference or broader configuration expansion.
- Archive-aware output inference for standalone `convert` or `convert-batch`.
- Redesign of standalone conversion or existing stack conversion beyond a
  genuinely necessary shared safety change.
- The separately identified repeat stack-TIFF collision/PARTIAL defect.

Any material defect or necessary change outside this boundary must be reported
and dispositioned separately rather than incorporated opportunistically.

## 3. CLI contract

Add the flag to the existing archive grammar:

```text
seestar-toolkit archive [-h] [--dry-run] [--location LOCATION]
                        [--hierarchy HIERARCHY]
                        [--source-action {copy,move}]
                        [--collision-policy {skip-identical,error,overwrite}]
                        [--non-interactive] [--config PATH]
                        [--convert-lights]
                        SOURCE_ROOT ARCHIVE_ROOT
```

`--convert-lights` is a boolean request applying only to that invocation. It is
generally compatible with all existing archive options. It adds no new mutually
exclusive combination and no `--unattended` option. Existing
`--non-interactive` archive context supplies the relevant explicit unattended
state; absence of usable interactive input must also be handled safely as
specified below. Global `--verbose` remains orthogonal.

Without `--convert-lights`, no individual-light TIFF operation is planned or
attempted. Existing stack-TIFF handling remains active and semantically
unchanged in both modes.

## 4. Authoritative observation layout

All newly planned archive observations use:

```text
observation_NN/
├── fits_images/
│   └── lights/
├── tiff_images/
│   └── lights/
└── seestar_stacked/
    ├── <stack>.fit
    └── <stack>.tiff
```

The diagram shows the possible complete structure; directory creation remains
lazy:

- Individual light FIT/FITS files belong in `fits_images/lights/`.
- Individual light TIFF derivatives belong in `tiff_images/lights/`.
- `fits_images/lights/` applies whether or not `--convert-lights` is supplied.
- `tiff_images/lights/` exists only when at least one actual light TIFF
  derivative exists. It must not be created merely by planning, dry-run,
  eligibility checking, a declined existing-FITS prompt or failed conversions.
- `seestar_stacked/` is unchanged and continues to contain the stack FITS and
  its companion TIFF together.
- Directories that are unnecessary for the particular lights-only, stack-only
  or mixed observation must not be created merely to realize the diagram.

Planning models and destination-collision checks must describe these paths
without mutating the filesystem. Execution must create only the parents needed
for an operation that has reached its mutation point.

Incremental reconciliation, observation-number allocation, archived-device
inspection, index reconstruction and all other archive observation-recognition
logic must consistently use `fits_images/lights/` for newly planned/current
archives. ENH-003 provides neither fallback recognition nor migration for the
historical `observation_NN/lights/` layout. Historical archives remain
untouched; they may not participate as recognized ENH-003 observations unless
separately migrated by future work.

## 5. Eligibility and operation order

### 5.1 Source and representation

Every light conversion input is the successfully established archived FITS at
`fits_images/lights/`, never the original source FITS. Archive orchestration
must call the existing authoritative `convert_fits_to_tiff(input, output)`
pipeline. It must not duplicate or fork FITS reading, Bayer demosaicing, RGB
normalization, data-type handling or TIFF writing.

An individual light is conversion-eligible only when:

1. discovery/reconstruction recognizes and accepts it as an individual light;
2. it has an authoritative planned archive destination;
3. the archived FITS has been successfully and verifiably established; and
4. the authoritative conversion pipeline supports that FITS representation.

Condition 4 is determined by attempting the established conversion pipeline,
not by inventing a second archive-specific support classifier. Unsupported or
unreadable content is an attempted conversion failure when conditions 1–3 have
been met. Ambiguous/unresolved observations and unsupported/unreadable source
FITS that never obtain an authoritative archived-light destination do not
become conversion candidates merely because the flag was supplied.

The stack remains outside the individual-light rules. Its existing derivative
planning, eligibility, location and reporting retain their current semantics.

### 5.2 Copy, move and established FITS outcomes

There is no separate conversion algorithm or collision behavior for copy and
move. The conceptual order for each eligible light is:

1. establish and verify the archived FITS;
2. for move, remove the source as the existing move workflow requires;
3. perform the requested light derivative processing when the archived FITS
   remains authoritatively established.

The following original outcomes are eligible:

- `COPIED`;
- `MOVED`;
- `SKIPPED_IDENTICAL`, where identity was established by the existing verified
  content comparison; and
- the narrow `PARTIAL` case in which the archive destination was successfully
  established and verified but deletion of the move source failed.

The implementation must represent or query the reason/evidence for `PARTIAL`;
it must not make unrelated partial results eligible by enum name alone. A
destination-establishment or verification failure is ineligible.

Existing FITS collision semantics remain authoritative:

- `collision-policy=skip-identical` with identical content produces
  `SKIPPED_IDENTICAL` and is eligible.
- `collision-policy=error` with any existing destination produces `COLLISION`,
  including when bytes happen to be identical, and is ineligible.
- ENH-003 must not rehash or reinterpret an explicit `COLLISION` into an
  eligible result.
- Other `COLLISION` and `FAILED` outcomes are ineligible.

Derivative failure never changes the original FITS outcome, removes the
archived FITS or attempts to restore a successfully moved source.

## 6. Candidate workspace and cleanup

Light TIFF candidates are generated beneath:

```text
observation_NN/tmp/
```

rather than at the final destination. The workspace is created lazily, only
immediately before an actual conversion attempt. Dry-run, no eligible lights,
declined processing of existing FITS and candidates rejected before conversion
must not create it.

ENH-003 candidate names must be unique and positively identifiable as
Toolkit-owned ENH-003 temporary files. The exact safe filename token is an
implementation detail, but it must be narrow enough that cleanup cannot match
ordinary user files by extension or a generic `tmp` substring. Candidate
creation must use exclusive semantics and must not follow a pre-existing
symlink or overwrite a pre-existing path.

Temporary candidates are never authoritative derivatives. An interrupted
operation must not promote a candidate on a later invocation. A later requested
ENH-003 conversion restarts from the authoritative archived FITS and may remove
stale files only when they positively match the ENH-003-owned convention.
Unknown or pre-existing files and directories in `tmp/` must never be removed,
rewritten or treated as candidates.

After each attempt, remove its Toolkit-owned candidate where possible. At the
end of the ENH-003 processing pass, remove remaining positively identified
stale ENH-003 candidates as appropriate, then remove `tmp/` only if it is empty.
Cleanup failure is a derivative-operation failure with a diagnostic when it
leaves an operation's safety/completion uncertain; it must never trigger broad
cleanup of unknown content. A pre-existing `tmp/` directory or unknown content
must be preserved.

## 7. Final destination and failure safety

The final primary name is derived from the archived FITS basename by the
established suffix-replacement convention and ends in `.tiff` under
`tiff_images/lights/`. Its only alternate is:

```text
<name>.tiff.duplicate
```

No numbered duplicate chain is permitted.

Create `tiff_images/lights/` only after a complete candidate has been generated
successfully and is ready for promotion. If every attempted conversion fails,
the operation must not leave a newly created empty derivative directory.
Directories or files that pre-dated the current invocation must not be removed
merely because no new TIFF succeeded.

Promotion and replacement must validate containment beneath the archive root
and reject symlink/path escapes using archive safety conventions. A new final
file must appear only as a complete candidate. Replacement must use a safe
same-filesystem transactional/atomic operation where the platform supports the
repository's existing contract; the old file must never be deleted before the
complete replacement candidate is ready. Any required relocation from
`observation_NN/tmp/` to a final sibling hierarchy must preserve that guarantee.

A failed conversion or derivative operation:

- preserves the archived FITS;
- leaves no incomplete/invalid final TIFF;
- preserves any existing valid primary or duplicate unless the user selected
  its successful replacement;
- cleans its owned candidate where possible;
- records an understandable diagnostic; and
- does not prevent independent remaining lights from being processed.

A genuine attempted light derivative failure contributes to a nonzero overall
command result. Failure to reach light processing because the FITS archive
operation already failed is reported through existing FITS reporting and must
not be duplicated as a light conversion failure.

## 8. Existing final TIFF behavior

Filename existence alone never proves that an existing primary TIFF matches
the authoritative archived FITS. Generate a fresh candidate in the temporary
workspace, then compute SHA-256 digests of the complete candidate and existing
primary TIFF. Digest equality is the required byte-identity test. Filesystem or
digest errors are derivative failures, not prompts or permission to overwrite.

### 8.1 Byte-identical primary

If candidate and primary are byte-identical:

- leave the primary untouched;
- remove the candidate;
- do not prompt;
- classify the result as `already present`; and
- treat it as successful/informational.

An unrelated existing `.duplicate` is not modified in this case.

### 8.2 Different primary, no duplicate

This is a genuine TIFF collision. When interactive input is usable, prompt:

```text
(K)eep both / (R)eplace existing / (S)kip conversion
```

Skip is the safe default wherever a default is required.

- **Keep both:** preserve the primary and promote the candidate as exactly
  `<name>.tiff.duplicate`. Classify as `duplicate created`.
- **Replace existing:** safely replace the primary with the complete candidate.
  Classify as `primary replaced`.
- **Skip conversion:** preserve the primary, discard the candidate and classify
  as `skipped`.

### 8.3 Different primary, duplicate already exists

Keep-both is unavailable. When interactive input is usable, prompt:

```text
(R)eplace duplicate / (S)kip conversion
```

- **Replace duplicate:** preserve the primary and safely replace the existing
  `.tiff.duplicate` with the complete candidate. Classify as
  `duplicate replaced`.
- **Skip conversion:** preserve both existing files, discard the candidate and
  classify as `skipped`.

Never create `.duplicate.2`, `.duplicate.3` or any other chain.

### 8.4 Unattended collision

When interactive input is unavailable, including the existing
`--non-interactive` archive context, select Skip without prompting. Preserve
the primary and any duplicate, discard the candidate, classify as `skipped`,
and do not make the command nonzero merely because of that skip.

These TIFF collision choices are separate from FITS `--collision-policy`.
That policy first determines whether the archived FITS is established and
eligible; it does not answer a later derivative collision prompt.

## 9. Previously archived identical FITS

With `--convert-lights`, the current invocation may process previously archived
individual-light FITS encountered through current planning/reconciliation as
verified `SKIPPED_IDENTICAL` results. This is a narrow backfill/verification
facility for the lights in the current archive operation, not a recursive scan
or archive-maintenance command. Do not discover unrelated observations or FITS
solely to increase this set.

Aggregate all such existing FITS into one decision before processing them. The
interactive presentation must communicate both the total and the state that is
knowable without conversion, for example:

```text
38 previously archived light FITS were found:
  20 require TIFF creation
  18 have existing TIFFs that can be verified

Process these existing FITS? [Y/n]:
```

Enter or Y processes all reported existing FITS. N processes none and reports:

```text
38 previously archived light FITS were left unchanged.
```

The default is Yes because the user explicitly supplied `--convert-lights`.
When input is unavailable, process them automatically. Declined files are not
TIFF `skipped` results because no TIFF operation was attempted. Newly copied or
moved lights do not participate in this aggregate consent question and are
processed automatically when the flag is present.

The pre-prompt split is observational only: an existing primary still requires
fresh candidate generation and digest comparison before it can be called
identical. The implementation must not claim that an existing filename has
already been verified.

## 10. Dry-run

`archive --dry-run --convert-lights` is completely non-mutating. It must:

- create no directories or files;
- generate no TIFF candidate;
- perform no candidate-dependent digest comparison;
- report no predicted conversion failure;
- make no conversion collision decision; and
- issue no existing-FITS processing prompt.

It may inspect existing destination state read-only and count determinate work.
Reporting must distinguish new primary destinations from existing primaries
that can only be compared during real conversion, for example:

```text
Light TIFFs:
  433 would be created
    5 existing TIFFs require comparison during conversion
```

Previously archived identical FITS may be counted and reported separately
without prompting or processing. Dry-run must not call the conversion pipeline,
infer that unsupported conversion will fail or classify a filename-only match
as `already present`.

## 11. Results, reporting and exit status

Normal results must be aggregated so hundreds of routine per-file success
messages are avoided. Report only categories with useful counts, using a block
equivalent to:

```text
Light TIFFs:
  432 created
    2 primary replaced
    1 duplicate created
    1 duplicate replaced
    3 already present
    2 skipped
    1 failed
```

The categories are deliberately disjoint:

- `created`: a new primary `.tiff` was promoted where none existed.
- `primary replaced`: a different existing primary was replaced by explicit
  interactive choice.
- `duplicate created`: Keep both promoted a new `.tiff.duplicate`.
- `duplicate replaced`: an existing `.tiff.duplicate` was replaced by explicit
  interactive choice.
- `already present`: a freshly generated candidate verified byte-identical to
  the existing primary.
- `skipped`: a genuine differing-TIFF collision was deliberately left
  unchanged after interactive or safe unattended selection.
- `failed`: an attempted conversion, comparison, promotion, replacement or
  required owned-candidate cleanup failed.

This classification clarifies the supplied reporting definition without
folding a replacement or alternate-file result into `created`. All four
successful write categories and `already present` are successful;
`already present` and `skipped` are informational and do not themselves make
the command nonzero. A declined aggregate existing-FITS group is reported
separately and contributes to none of these categories.

For each failure, print a concise diagnostic containing the light basename and
the conversion/derivative reason, for example:

```text
Light TIFF conversion failed:
  Light_M45_30s_017.fit
  <conversion error/reason>
```

Continue processing independent lights. Do not duplicate routine success
messages unless existing `--verbose` conventions explicitly call for detail.

`failed > 0` produces a nonzero overall command result under the repository's
existing archive exit convention. Existing FITS, planning, stack-TIFF and index
problems continue to affect status as they do now. A light skip, verified
already-present result, or declined existing-FITS group does not independently
make the command nonzero. When FITS preservation succeeded but one or more
light derivatives failed, final output must say both, for example:

```text
Archive FITS preservation completed successfully.
One or more requested light TIFF conversions failed.
```

The structured result model must retain enough disjoint state to derive these
counts and aggregate status without parsing diagnostics.

## 12. Observation forms and unchanged behavior

- **Lights-only:** use `fits_images/lights/`; optionally create light TIFFs.
  Do not invent a stack or create `seestar_stacked/` unnecessarily.
- **Stack-only:** naturally has no light conversions. Existing stack FITS/TIFF
  behavior remains unchanged and `tiff_images/lights/` is absent.
- **Mixed:** apply the new light layout and optional light processing while
  retaining the stack pair in `seestar_stacked/`.
- **Empty input:** retain the existing no-op and create nothing.
- **Ambiguous, unresolved or unsupported inputs:** retain existing discovery,
  reconstruction and planning behavior; the flag grants no destination.

The known behavior in which repeat processing of an existing Seestar stack TIFF
may be classified as a collision/PARTIAL remains unchanged. ENH-003 tests must
lock that boundary rather than silently fixing it while changing light TIFFs.

## 13. Architecture constraints

Keep these responsibilities separated:

- planning determines new FITS and optional TIFF destinations without I/O;
- FITS execution establishes originals and retains collision-policy authority;
- archive orchestration selects eligible archived FITS, prompts and aggregates;
- the conversion service remains the sole pixel-conversion pipeline;
- a focused derivative finalization boundary owns candidate digest comparison,
  promotion/replacement and duplicate policy;
- indexing reads authoritative archived FITS from the new layout and must not
  treat TIFFs or temporary files as source evidence.

Shared safety changes to allow a complete candidate at an explicit path are
permitted only when genuinely required, with standalone `convert` and
`convert-batch` behavior and exclusive-destination guarantees preserved. Do not
make archive prompting or archive collision policy part of the conversion
service. Do not overload existing stack behavior with ENH-003 light-specific
collision semantics.

Observation recognition must be strict enough that `tiff_images/lights/` or
`tmp/` alone cannot establish an archive observation. Authoritative archived
FITS in `fits_images/lights/` and/or the existing valid stack evidence are the
relevant content. Symlink and archive-root containment checks remain mandatory
for reads, workspace creation and final mutations.

## 15. Documentation and future-work boundary

At implementation time, update applicable archive help, user guides,
architecture, project notes, changelog/change records and generated
documentation artifacts according to repository conventions. Historical Stage
documents remain historical and must not be rewritten to pretend the new layout
existed earlier.

ENH-003 must not unnecessarily obstruct:

1. future archive-aware `convert`/`convert-batch` output inference into
   `tiff_images/lights/` when operating in a recognized archive; or
2. a future archive TIFF-verification command that regenerates candidates from
   authoritative FITS and compares digests.

Neither feature is authorized here, and the future verification command's CLI
is deliberately undecided.
